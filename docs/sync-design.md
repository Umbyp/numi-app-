# การ sync ข้ามเครื่องของ Numi — การออกแบบ

เอกสารนี้ตัดสินใจเรื่อง **conflict resolution** ก่อนเขียนโค้ด sync จริง
เพราะการแก้ schema ทีหลังเมื่อมีข้อมูลผู้ใช้อยู่บนเซิร์ฟเวอร์แล้วราคาแพงมาก

Backend ที่เลือก: **Supabase** (Postgres + Auth + Row-Level Security)
แต่ทุกอย่างในเอกสารนี้เป็นฝั่ง client ทั้งหมด ย้าย backend ทีหลังได้โดยไม่ต้องรื้อ

---

## 1. หลักการสามข้อ

### 1.1 เซิร์ฟเวอร์เป็นเจ้าของเวลา ไม่ใช่เครื่องผู้ใช้

นาฬิกาบนมือถือเชื่อไม่ได้ ผู้ใช้ตั้งเวลาเองได้ timezone เปลี่ยนได้ เครื่องที่แบตหมด
นานอาจกลับไปปี 1970 ถ้าใช้ `updated_at` ที่เครื่องเขียนเองมาตัดสินว่าใครใหม่กว่า
เครื่องที่นาฬิกาเดินหน้าไป 1 ปีจะชนะทุกครั้งตลอดไป และผู้ใช้จะไม่มีทางแก้ได้เลย

จึงแยกเป็นสองค่า

| คอลัมน์ | ใครเขียน | ใช้ทำอะไร |
|---|---|---|
| `updated_at` | เครื่อง | แสดงผลใน UI เท่านั้น ห้ามใช้ตัดสินการชน |
| `server_updated_at` | เซิร์ฟเวอร์ | ตัวตัดสินว่าแถวไหนใหม่กว่า และเป็น cursor ตอน pull |

**ฝั่ง client ไม่ใช้เวลาของตัวเองเลือกว่าจะ push อะไร** แต่ใช้ธง `dirty`
แถวไหนถูกแก้ก็ตั้ง `dirty = 1` push สำเร็จแล้วเซิร์ฟเวอร์ตอบ `server_updated_at` กลับมา
ค่อยล้างธง วิธีนี้ปัญหานาฬิกาเพี้ยนหายไปทั้งหมดโดยไม่ต้องทำ vector clock ให้ซับซ้อน

### 1.2 ลบแล้วต้องเหลือหลุมศพ

ถ้าลบแถวออกจาก SQLite จริง ๆ ตอน pull ครั้งถัดไปเซิร์ฟเวอร์จะส่งแถวนั้นกลับมาใหม่
เพราะไม่มีอะไรบอกว่ามันถูกลบไปแล้ว **มื้ออาหารที่ลบทิ้งจะฟื้นขึ้นมาเองทุกครั้งที่ sync**

ทุกตารางที่ sync จึงใช้ `deleted_at` แทนการลบจริง query ทั้งหมดต้องกรอง
`deleted_at IS NULL` และมีงานเก็บกวาดลบหลุมศพที่เก่ากว่า 90 วันทิ้งเป็นระยะ

### 1.3 id สร้างจากเครื่อง และรูปแบบของ id คือการตัดสินใจเรื่อง conflict

นี่คือจุดที่คนพลาดบ่อยที่สุด **รูปแบบการตั้ง id เป็นตัวกำหนดว่าข้อมูลจะทับกันหรือบวกกัน**

| ต้องการให้ | id ต้องเป็น | ตัวอย่าง |
|---|---|---|
| ทับกัน — เก็บอันล่าสุด | ผูกกับวัน | `w_2026-09-09` (ชั่งน้ำหนักวันละครั้ง) |
| บวกกัน — เก็บทุกอัน | สุ่ม | `meal_1757..._483920` (มื้ออาหาร) |

ตั้งผิดแบบแล้วข้อมูลหายเงียบ ๆ โดยไม่มี error ให้เห็น

## 2. ตารางแบ่งตามพฤติกรรมตอนชน

### กลุ่ม A — แถวเหตุการณ์ (ปลอดภัยกับ LWW)

`meal_entries` · `workouts` · `chat_messages` · `foods` · `workout_plan_completions` · `meal_templates`

สร้างครั้งเดียวบนเครื่องเดียว id สุ่ม แทบไม่มีโอกาสชนกันเลย
สองเครื่องบันทึกคนละมื้อ = สองแถว ไม่ทับกัน ถูกต้องตามที่ควรเป็น

> `meal_templates.use_count` เป็นตัวนับที่ชนได้ (ใช้มื้อชุดจากสองเครื่องตอนออฟไลน์
> แล้วยอดนับหายไปหนึ่ง) แต่มันเป็นแค่ตัวเลขไว้เรียงลำดับความถี่ ไม่ใช่ข้อมูลของผู้ใช้
> ยอมให้เพี้ยนได้ ไม่คุ้มที่จะทำ CRDT

### กลุ่ม B — แถวหนึ่งต่อหนึ่งวัน (LWW ถูกต้องแล้ว)

`weights` · `measurements`

`localDate` เป็น UNIQUE และ id ผูกกับวันอยู่แล้ว (`w_2026-09-09`)
สองเครื่องกรอกน้ำหนักของวันเดียวกัน → แถวเดียวกัน → อันที่พิมพ์ทีหลังชนะ
ซึ่งตรงกับที่ผู้ใช้คาดหวัง ไม่ต้องแก้อะไร

### กลุ่ม C — แถวสถานะเดี่ยว (LWW พอรับได้)

`profile` (แถวเดียว id=1) · `app_settings`

แก้ส่วนสูงบนเครื่องหนึ่ง แก้เป้าหมายบนอีกเครื่องตอนออฟไลน์ → เสียไปหนึ่งการแก้
การ merge ระดับ field แก้ได้แต่ซับซ้อนขึ้นมาก และคนแทบไม่แก้โปรไฟล์สองเครื่องพร้อมกัน
**ยอมรับ LWW ไปก่อน** ถ้าเจอปัญหาจริงค่อยแยก `profile` เป็น key-value เหมือน `app_settings`

### กลุ่ม D — ตัวนับสะสม (LWW ทำข้อมูลหาย ต้องแก้ schema)

`water_logs` ← **ต้องแก้ก่อน sync**

ดูหัวข้อถัดไป

## 3. ปัญหาที่ต้องแก้ก่อน — `water_logs`

ตอนนี้เก็บ **ยอดรวมของวัน** ไว้ในแถวเดียว id เป็น `water_2026-09-09`

```
water_logs: { id: 'water_2026-09-09', local_date: '2026-09-09', ml: 1500 }
```

คอมเมนต์ใน schema เขียนเหตุผลไว้ว่า *"เก็บยอดรวมของวัน ไม่ได้เก็บทีละแก้ว
เพราะสิ่งที่คนอยากรู้คือวันนี้ดื่มไปเท่าไหร่แล้ว"* — **เหตุผลนี้ถูกต้องสำหรับแอปเครื่องเดียว
แต่ใช้ไม่ได้ทันทีที่มี sync**

### ทำไมถึงพัง

| เวลา | มือถือ | แท็บเล็ต (ออฟไลน์) | ค่าที่ควรเป็น |
|---|---|---|---|
| 09:00 | +500 → `ml = 500` | — | 500 |
| 12:00 | — | +750 → `ml = 750` | 1250 |
| 13:00 sync | | | **ได้ 750 หายไป 500** |

ทั้งสองเครื่องเขียน id เดียวกัน แถวเดียวกัน และค่าที่เขียนเป็น**ยอดรวม**ไม่ใช่**ส่วนต่าง**
LWW จึงเลือกยอดรวมของเครื่องที่ sync ทีหลังมาทับ น้ำที่ดื่มจากอีกเครื่องหายทั้งก้อน
ไม่มี error ไม่มีคำเตือน ผู้ใช้เห็นแค่ตัวเลขลดลงเอง

### วิธีแก้ — เปลี่ยนตัวนับเป็นบันทึกเหตุการณ์

แยกเป็นตารางใหม่ `water_intakes` เก็บ**ทีละครั้งที่กด** id สุ่ม

```
water_intakes: { id: 'water_1757..._29184', local_date: '2026-09-09', ml: 500 }
water_intakes: { id: 'water_1757..._77310', local_date: '2026-09-09', ml: 750 }
```

ยอดของวัน = `SUM(ml)` สองเครื่องออฟไลน์ได้สองแถวคนละ id ทั้งคู่รอด รวมได้ 1250 ถูกต้อง
นี่คือรูปแบบมาตรฐานของการทำตัวนับให้ sync ได้ — **เปลี่ยนตัวนับเป็น log แล้วรวมตอนอ่าน**

ปุ่มลบ (−250) ก็เก็บเป็นแถวค่าติดลบ `ml = -250` ผลรวมยังถูกต้อง
และได้ของแถมคือรู้ว่าดื่มตอนกี่โมงบ้าง ซึ่งทำกราฟได้ในอนาคต

ต้นทุน: วันหนึ่งได้ราว 4-8 แถว ปีหนึ่งไม่ถึง 3,000 แถว ไม่มีนัยต่อขนาดหรือความเร็ว

## 4. คอลัมน์ที่เพิ่มทุกตารางที่ sync

```sql
user_id           TEXT              -- null จนกว่าจะล็อกอิน
updated_at        INTEGER NOT NULL  -- เวลาเครื่อง ใช้แสดงผลเท่านั้น
server_updated_at INTEGER           -- เวลาเซิร์ฟเวอร์ ใช้ตัดสินการชนและเป็น cursor
deleted_at        INTEGER           -- หลุมศพ
dirty             INTEGER NOT NULL DEFAULT 1  -- 1 = ยังไม่ได้ push
```

`dirty` ตั้งต้นเป็น `1` เพราะข้อมูลที่มีอยู่แล้วในเครื่องก่อนเปิดใช้ sync
ต้องถูก push ขึ้นไปทั้งหมดในรอบแรก

### ตารางใหม่สำหรับ cursor

```sql
CREATE TABLE sync_meta (
  table_name     TEXT PRIMARY KEY,
  last_pulled_at INTEGER NOT NULL DEFAULT 0  -- server_updated_at สูงสุดที่ดึงมาแล้ว
);
```

## 5. `app_settings` — ไม่ใช่ทุก key ที่ควร sync

บาง setting เป็นของเครื่อง ไม่ใช่ของคน การ sync จะทำให้รำคาญ

| key | sync | เหตุผล |
|---|---|---|
| `theme` | ✗ | มือถือใช้ธีมมืดตอนกลางคืน แท็บเล็ตบนโต๊ะใช้สว่าง เป็นคนละบริบท |
| `celebrated_date` | ✗ | กันแอนิเมชันเด้งซ้ำ เป็นสถานะ UI ของเครื่องนั้น |
| `reminder_*` | ✓ | ตั้งเวลาเตือนไว้แล้วควรได้เหมือนกันทุกเครื่อง |

ใช้ allowlist ตายตัวในโค้ด ไม่ใช่ blocklist — key ใหม่ที่ยังไม่ตัดสินใจจะได้ไม่หลุดขึ้นเซิร์ฟเวอร์เอง

## 6. อัลกอริทึม

```
push:  แถวที่ dirty = 1  →  POST  →  เซิร์ฟเวอร์เขียนทับตาม server_updated_at
                                  →  ตอบ server_updated_at กลับมา  →  dirty = 0

pull:  GET rows WHERE server_updated_at > sync_meta.last_pulled_at
       สำหรับแต่ละแถว:
         ถ้า local.dirty = 1  → มีการแก้ที่ยังไม่ push เก็บของ local ไว้ (push รอบหน้าจะทับ)
         ถ้าไม่                → เขียนทับด้วยของเซิร์ฟเวอร์
       อัปเดต last_pulled_at
```

**push ก่อน pull เสมอ** เพื่อลดโอกาสที่ของ local จะถูกทับ

## 7. ช่องว่างที่รู้อยู่แล้ว — ต้องปิดก่อนเปิด sync จริง

`updated_at` ใช้ `$defaultFn` ของ drizzle ซึ่ง **ทำงานเฉพาะตอน insert เท่านั้น**
ทุกจุดที่ `UPDATE` ยังต้องเซ็ต `updatedAt` และ `dirty = 1` เอง ซึ่งลืมได้ง่ายมาก
และถ้าลืม แถวนั้นจะไม่ถูก push ขึ้นเซิร์ฟเวอร์เลยโดยไม่มี error ให้เห็น

ทางแก้ที่ตั้งใจจะใช้คือ **SQLite trigger ต่อตาราง**

```sql
CREATE TRIGGER trg_<table>_dirty AFTER UPDATE ON <table>
FOR EACH ROW WHEN NEW.dirty = OLD.dirty   -- ไม่ยิงตอน sync engine ล้างธงเอง (1 -> 0)
BEGIN
  UPDATE <table> SET updated_at = CAST(strftime('%s','now') AS INTEGER) * 1000, dirty = 1
   WHERE rowid = NEW.rowid;
END;
```

ยังไม่ใส่ใน PR นี้เพราะต้องทดสอบเรื่อง `recursive_triggers` ของ expo-sqlite ให้แน่ก่อน
(ค่าเริ่มต้นของ SQLite คือปิด ซึ่งทำให้ปลอดภัย แต่ไม่ควรพึ่ง pragma โดยไม่ยืนยัน)

## 8. ยังไม่ตัดสิน

- **ล็อกอินด้วยอะไร** — Apple / Google / magic link · Apple บังคับให้มี Sign in with Apple ถ้ามี social login ตัวอื่นบน iOS
- **ข้อมูลที่มีอยู่ก่อนล็อกอิน** — ผู้ใช้ที่ใช้มาแล้วสามเดือนแล้วเพิ่งสมัคร ต้องยกข้อมูลเดิมขึ้นบัญชีใหม่ ห้ามหาย
- **สองบัญชีบนเครื่องเดียว** — ต้องล้าง SQLite ตอนสลับบัญชี ไม่งั้นข้อมูลปนกัน
- **รูปอาหาร** (`meal_entries.photo_uri`) — เป็น path ในเครื่อง sync ไม่ได้ตรง ๆ ต้องอัปขึ้น Supabase Storage หรือยอมให้เป็นของเครื่องเดียว

## 9. กติกาเดิมที่ห้ามหลุด

เอกสารนี้ไม่แตะกติกาใน roadmap แต่มีสองข้อที่เกี่ยวกับกลุ่ม B โดยตรง

- **ตารางอันดับต้องปิดได้** — ค่าตั้งต้นควรเป็นปิด ไม่ใช่เปิด
- **ข้อมูลน้ำหนักเป็นเรื่องอ่อนไหว** — ตอนแชร์ความคืบหน้าต้องเลือกได้ว่าให้เห็นอะไร
  ค่าตั้งต้นคือไม่แชร์น้ำหนักตัว Row-Level Security ของ Supabase บังคับได้ตั้งแต่ระดับฐานข้อมูล
